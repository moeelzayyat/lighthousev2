**Date:** 2026-10-16 · **Scope:** repo `moeelzayyat/lighthousekeepers`, branch `multiship-test` at 78cc6c9 (pending batch 763dc4d), `docs/progress.md`, `IMPLEMENTATION_LOG.md`, the multi-ship plan and packages, and all ~21k lines of Luau under `src/`.
**Method:** document review, an independent read of every source file with file:line findings, verification of the two highest-severity findings by hand, the Roblox player-psychology audit framework, and a check of the live Roblox page.
**Evidence tags:** `[Code]` verified in source · `[Docs]` from the project's own documents · `[Official]` Roblox Creator Hub · `[Practitioner]` creator sources in the audit skill · `[Inference]` my reasoning · `[Assumption — test]` must be validated by players.

## 1. Summary

**The game is built and it is good.** A complete 13-night co-op loop with a unique core verb (aiming a lighthouse beam), four real roles, bosses, an economy, forecasts, evolutions, a coach, a polished mobile HUD and a published place. That is far more than most Roblox projects ever reach, and the economy code has real discipline (server-made tools, idempotent request IDs on shop/trader/loadout). `[Code]` `[Docs]`

**The problem is where the last three days went.** Since the Oct 13 publish, nearly all effort has gone into splitting the game into Harbor and Isle places with reserved servers, teleports, a MemoryStore manifest, a hand-written session lock, and a 13-task save-integrity audit trail — while the live game has had **zero outside playtests**, is still listed as **"Lighthouse Keepers - Staging"**, and shows **no visible players**. `[Docs]` That infrastructure solves a scaling problem a game with full 60-player servers would have. This game's problem is that nobody has played it yet.

**Meanwhile the real data risk is in production, not in the test branch.** Production saves use a blind `UpdateAsync` overwrite with no session lock and a single save attempt on leave. A quick rejoin or one transient error after a run can lose the Pearls that were just awarded. `[Code: PlayerData.luau:145–149, 427–428]` The session-lock work was aimed at the multi-ship hand-off; the simpler, bigger win is to protect production today with ProfileStore.

**Verdicts**

| Lens | Verdict | One line |
|---|---|---|
| Player psychology | **PROTOTYPE** (confidence Medium) | Stop building, start measuring: the loop is plausible and can be in front of real players within days. |
| Technical architecture | **REVISE** | Working monolith with sound economy security; production persistence unsafe; multi-ship code has two HIGH bugs; no tests in the repo; phone performance risk. |
| Pending batch 763dc4d | **ACCEPT WITH CORRECTIONS** — do not publish before corrections 1–2 | See §6. |
| Process | **REVISE** | The per-task auditor-package workflow is costing more than it protects; replace with the checkpoint protocol while keeping every hard rule. |

**The single decision that unblocks everything (D-001 in the new decision log):** park the Harbor/Isle split. Run **one crew per server** (server size 4, the harbor is the crew's own deck), protect production saves with ProfileStore, and spend the next two weeks on first session, run length, store presence, telemetry and a public test. The multi-ship branch stays frozen as future scaling, to be revived only when server-fill data says servers are full.

## 2. Technical audit

### 2.1 What's strong (keep)
- **Server authority on everything that matters.** Damage, creature positions, Shells, Pearls and loot are never client-controlled. Tools are server-made; `Attack` validates weapon = equipped Tool attribute, cooldown and range. `[Code: Main.server.luau:516–561]`
- **Idempotent economy requests** with `requestId` replay on Shop (capped `handled` map), Trader and Loadout. `[Code: ShopService.luau:181–208]`
- **Dependency-injected roster/boarding/departure modules** with real fake-service tests in the packages (18/18, 19/19). `[Docs]`
- **The session lock itself** (`SessionLock.luau`): metadata-based, fenced by token, atomic claim, FIFO per key. Sound design, thin operational layer. `[Code]`
- **Telemetry foundation**: `EventLog` already records a per-player onboarding funnel (crew 15.6 s → landed 26.1 s → first action 29.9 s → lamp 42.1 s → first beam hit 50.3 s, scripted). `[Docs]` This is the funnel a public test needs; it only has to be wired to Roblox `AnalyticsService`.
- **Measured server performance**: 60 Hz, 0.11 ms game work per frame, ~50 KB/s per player with the swarm (solo). `[Docs]`

## 3. Player-psychology audit

### Snapshot
- **Premise as a stranger hears it:** "Four friends keep a lighthouse lit through 13 storm nights — one aims the beam, the others haul oil, repair the tower and fire cannons at sea monsters."
- **Primary segment:** older kids / young teens (10–14), phone and PC, playing with 1–3 friends. Secondary: parents or older siblings playing with kids (cozy co-op). `[Inference]`
- **Need served:** belonging + competence ("we nearly lost the light and saved it together"); the Keeper gets power/mastery.
- **Closest incumbents:** co-op wave/tower-defense survival on Roblox. Nothing I found uses a lighthouse beam as the weapon. `[Inference; incumbents not benchmarked]`
- **Team:** solo owner + Claude as developer. Game already built.

### Walkthrough (12-year-old on a phone, joins alone)
- **Icon & title:** "Lighthouse Keepers - Staging" on a store tile. "Staging" reads as broken or unfinished. No tested icon. `[Docs]`
- **0–30 s:** fast path works — on the crew in ~1 s, lands at ~12 s, prologue storm. Good. First beam hit ~50 s (scripted upper bound of speed). `[Docs]`
- **30 s–2 min:** must learn the lamp *and* oil in 2.5 minutes, solo. If they don't carry oil the lamp dies in night 1 and the run ends in **Defeat, 0 Pearls, ~2.5 min in**. That is the most likely first-session outcome for an unassisted phone player. `[Docs: progress.md §3 run timing]` `[Assumption — test]`
- **2–10 min:** if they survive, a 13-night run is **~27 minutes**. A phone player's first win is a long commitment; a loss on night 4 pays 3 Pearls and shows a 30-Pearl Storm Harpoon as "next goal". `[Docs]`
- **Day 2:** returns if a friend is coming or a goal is close. Nothing waits for them (no daily, no collection, no leaderboard).

### Section findings
1. **Audience fit (2)** — Clear co-op fantasy; demand assumed, not shown. No incumbent research in the docs. `[Assumption — test]`
2. **Click appeal (1)** — Title is literally "Staging"; no icon tested; the brief exists. The fantasy itself is highly clickable ("what is that enormous thing outside the lighthouse?"). `[Docs]`
3. **First session (2)** — Time-to-control excellent (`[Docs]`); the 0-Pearl 2.5-minute defeat is the bounce risk. Nothing in the first 60 s requires reading? The coach prompts are text + marker; the marker carries it. `[Practitioner: first action = fun action; Official: <60 s and 61–180 s bounce windows]`
4. **Core loop (2)** — Rich decisions for the Keeper; oil-carrier is a chore unless the crew feed and clutch-save moments make it feel heroic (they try to). 27-minute runs are long for the segment; the Roblox playtime signal caps at 60 min/day anyway. `[Official]` Shells pile up late (~1,180 per win) so bench choices stop mattering mid-run. `[Docs §12]`
5. **Progression & return (2)** — Pearls 1/night + 5/win; prices 30–140; a Storm Harpoon ≈ 2 wins ≈ 1 hour. Reasonable for a win, slow for a loser. No offline progress, no collection, no daily objective. Positive: losing still pays per night survived. `[Docs]`
6. **Social (3)** — Co-op is the game; lamp shift, crew feed, invites, forecast vote. Losers keep per-night Pearls. Griefing: a Keeper who aims away is released after 25 s idle; acceptable. `[Docs]`
7. **Differentiation (3)** — Proven base (co-op wave defense) + an only-yours verb (the beam) + a role structure. This is the project's best asset.
8. **Monetization (2)** — Nothing enabled; policy is sound (cosmetics Robux-only, convenience only if earnable, never power, no paid crates). Fairness test passes by design; there is simply no revenue path yet. `[Docs]`
9. **Execution risk (2)** — The game exists (huge). Risk is now **direction and process**: three days of infrastructure, 400+ doc files, no playtest. `[Docs]` `[Practitioner: documented flops were grand projects that never met players]`
10. **Validation (2)** — Pass thresholds already written in `progress.md §13` (≥80% understand fuel, ≥70% use both beam modes, ≥60% rematch). Nothing has been run.

### Playtest plan (Stage S3 in the roadmap)
- **Build:** current game + improvements 1–5 above. No multi-ship.
- **Riskiest assumptions, in order:** unassisted phone players survive Night 1 ≥ 50%; ≥ 60% rematch or sail again; both beam modes used on purpose ≥ 70%; the oil role is described as fun by at least some testers.
- **Testers:** 5+ sessions of 2–4 players, at least one real phone each, one session with no verbal help (already specified in `PLAYTEST_KIT.md`).
- **Measure:** first-play bounce (<60 s, 61–180 s), D1 play days, co-play days, qualified sessions `[Official]`; plus the funnel above.
- **Upgrade if:** Night-1 survival ≥ 50% and rematch ≥ 60%. **Downgrade if:** Night-1 survival < 30% after two FTUE passes.

## 4. Process audit

The owner's own rules (never publish without approval, protect production saves, API off before Play, back up before edits, never touch the other games on the PC) are right and stay verbatim in `CLAUDE.md`. What should change is the shape of the work:

- **Per-task auditor packages** (AUDITOR_REPORT, CHANGE_MANIFEST, TEST_EVIDENCE, AUDITOR_QUESTIONS, ZIPs, before/after copies, hash comparisons) for every task produced 400+ files and a 13-task sequence to test a save path. The checkpoint protocol (tests pasted, play test console, numbers, restore point, mirror commit, one handoff record, one approval line) keeps the evidence standard with a tenth of the overhead.
- **The external-auditor relay** (ChatGPT as "The Architect") doubled every cycle. Keep an independent review only at stage gates (S1 production cutover, S3 GO/NO-GO, launch), not per task.
- **Hashes and before/after copies** are replaced by the `src/` mirror export after each checkpoint plus Studio restore points — the same information, already in Git.

## 6. Verdict on the pending batch — commit 763dc4d (Isle arrival and return)

**ACCEPT WITH CORRECTIONS. Do not publish to the test places before corrections 1 and 2.**

What the diff does is internally consistent and the Studio evidence supports the spawn move, the landing card and cover text, the `arrivedFromIsle` pure cases and the report counts. `SourcePlaceId` is server-populated and used only for routing. Mirroring the deployed Config in git is the safer state and the package's reasoning is right.

**Corrections**
1. **Isle join race (Finding 2).** In `Voyages.returnToHarbor`: if the player has no live profile and no frozen profile, skip the hand-off and teleport directly; if a load is in flight, wait for it before the hand-off; if the teleport cannot be issued, **kick** — the current recovery message is wrong on the isle.
2. **`reclaim` guard (Finding 1).** `PlayerData.reclaim` must refuse unless `frozen[player] ~= nil and WRITABLE[player.UserId]`, and must never create a profile. `Voyages.teleportFailed` must skip reclaim (and the kick) when the hand-off was refused because there was nothing to hand off. The package's §5 claim that a second account "plays memory-only and is never saved" is false as the code stands.
3. Call `deps.report(0, expectedCount)` on `IsleAdmission.init` and when `closed`, so a refused player never sees "LANDING 0/0"; better, give refused players their own card text.
4. Add 3 retries with backoff to `Voyages.readManifest` before any multi-crew test (Finding 10).
5. Correct the package text in §5.

**If D-001 (one crew per server) is adopted, this batch and the multi-ship branch are frozen rather than corrected**; the corrections above still stand as the record of what must be true before that branch is ever revived.
